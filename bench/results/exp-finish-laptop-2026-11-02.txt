# ExpBenchmark on the owner's laptop under -XX:UseAVX=2, 2 November 2026: the per-lane finish
# before and after it was made allocation-free, and the finish at SPECIES_MAX, where it still boxes
#
# LAPTOP NUMBERS, NOT HEADLINES. -XX:UseAVX=2 makes C2 compile as for an AVX2 host (GitHub's x86
# runners and the EPYC 7763 benchmark hosts). On the EPYC 7763 the finish arm as first merged was
# 1.64x slower than the blend on mixed data (exp-epyc7763-2026-11-02.txt). The EPYC run of this
# change decides between the arms; this file decides nothing.
#
# Why:         finish256 allocated 52928 B/op on mixed data. The fix writes the per-lane finish
#              out inline in Exp's body; these runs check that it no longer allocates and how
#              the two arms move relative to each other. The After runs also measure finishMax
#              and blendedMax, at DoubleVector.SPECIES_MAX, where the finish still boxes.
# Before:      9965b6c (main then; the finish in a separate method, finishPerLane)
# After:       f2b76e9422c6b8142df4843e7c506ed14cef11de (branch exp-finish-no-alloc, with main's
#              cbc60d2 merged, whose Lanes.intSpecies picks the int species by vectorBitSize();
#              the finish written out inline: toLong, lane, withLane). The run checked that no
#              tracked file differed from that commit before it started; at its end the commit
#              was the same and only SKILLS.md, a document, had been edited. This replaces a
#              first After run made on uncommitted code, which had no commit to name.
# Span:        Before and After lie on either side of cbc60d2. Its changes reachable from Exp
#              are Lanes.intSpecies alone (the others are a warning printed once in Faults'
#              initialiser and Javadoc). At 128, 256 and 512 bits that method returns the same
#              named IntVector species as before, so the vector bodies measured are inferred to
#              be the same, not measured to be; the unchanged common-data finish256 rows (1933
#              before, 1952 after) are consistent with that.
# JDK:         OpenJDK 64-Bit Server VM (build 25.0.4.1+1-1-26.04.4-Ubuntu, mixed mode, sharing)
# CPU:         AMD Ryzen AI 9 HX PRO 370 w/ Radeon 890M
# Vector:      -XX:UseAVX=2 -XX:MaxVectorSize=32 (preferred and max species 256 bits); the
#              512-bit section at the end runs at the laptop's default flags (max species 512)
# Kernel:      7.0.0-42-generic
# Load:        other agents share the machine; each run waited inside the lock for the one-minute
#              load average to fall under 1.0
#              before: load average: 0.88, 1.56, 1.61 at start;
#                load average: 1.05, 1.39, 1.54 at end
#              after: load average: 0.84, 1.57, 1.50 at start;
#                load average: 1.26, 1.37, 1.43 at end
#              before-rerun: load average: 0.93, 1.16, 1.25 at start;
#                load average: 1.07, 1.13, 1.22 at end
#              (24 logical cores)
# JMH 1.37:    -f 2 -wi 3 -w 2s -i 5 -r 2s -prof gc
#              -jvmArgsAppend "-XX:UseAVX=2 -XX:MaxVectorSize=32
#              -XX:CompileCommand=inline,io.github.vecbricks.vfdlibm.*::*"
#              (the body inlined into the loop, as Varka emits it)
# Command:     java --add-modules jdk.incubator.vector -cp <test classpath> org.openjdk.jmh.Main
#              "ExpBenchmark.(finish256|blended256)$" <the options above>; the After run went
#              through the jmh profile, which runs that same command:
#              mvn -B -q -Pjmh exec:exec -Djmh.args="ExpBenchmark.(finish256|blended256|
#              finishMax|blendedMax)$ <the options above> -rf json"
# Array:       1024 doubles; common = uniform [-20, 20]; mixed = one input in 16 replaced by NaN,
#              800, -750 or -708.5 (62 of the 256 4-lane vectors hold a rare lane, 66 lanes)
#
# Where the 52928 B/op came from:
# - -XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining, before: in the final compile of the
#   benchmark loop, "Exp::finishPerLane (59 bytes) failed to inline: NodeCountInliningCutoff".
#   CompileCommand=inline lifts the size limit, not the node-count cutoff, so the call stayed a
#   call, and x, result and the rare mask reached it as heap objects.
# - They were boxed on every vector, rare or not, and the rare vectors also paid the call's own
#   arrays: 256 vectors x 168 B (two 64-byte Double256Vector boxes, a 40-byte Double256Mask)
#   = 43008 B, plus 62 rare vectors x 160 B (two toArray copies of 48 B and the 64-byte returned
#   vector) = 9920 B, sum 52928 B/op, exactly the measured figure. JFR (settings=profile) on a
#   loop of the same body named, by allocation site, DoubleVector.fromArray0Template,
#   DoubleVector.blendTemplate, Double256Mask.or and DoubleVector.toArray (that recording is not
#   kept). On common data the branch never ran, C2 compiled it as an uncommon trap, and nothing
#   boxed.
# - After: no call into vfdlibm at the end of the body; the Vector API's own toLong, lane and
#   withLane are inlined late instead of refused. On mixed data finish256 reads 0.009 B/op and
#   finish512 0.007 B/op (the AFTER tables below).
#
# SPECIES_MAX (finishMax, blendedMax; the After runs only):
# - finishMax allocates on mixed data: 36992 B/op under UseAVX=2 (256 bits) and 30912 B/op at
#   the default flags (512 bits), where finish256 and finish512, the same shapes, read 0.009 and
#   0.007. On common data, where the finish never runs, it reads 0.007 and 0.005; blendedMax
#   reads 0.016 or less everywhere.
# - Why, -XX:+UnlockDiagnosticVMOptions -XX:+PrintIntrinsics at f2b76e9, default flags, mixed
#   data, one fork (-f 1 -wi 2 -w 1s -i 1 -r 1s, the body inlined): in finish512,
#   "VectorSupport::extract (35 bytes) (intrinsic) late inline succeeded" and the same for
#   VectorSupport::insert, 56 lines each; in finishMax, both "failed to inline (intrinsic)",
#   after "** missing constant: vclass=ConP etype=ConP vlen=ConI idx=CountTrailingZerosL": the
#   lane index the finish computes from the mask's bits is not a constant, and at the Max shape
#   the lane access is not intrinsified without one. Both runs also print the "not supported
#   ... op=store ... atype=byte" lines the fixed shapes print; the allocation rate, not those
#   lines, is the verdict (SKILLS.md).
# - bench/alloc-check.py leaves the *Max rows out (its INCLUDE regex), so CI does not fail on
#   this known box.
# - Ratios: before, mixed finish256 and blended256 were within 1.3x, so the before run was
#   repeated; the re-run is at the end and agrees. After, every finish/blend ratio at 256 and
#   512 bits is over 1.3x. The same holds at 512 bits (the last section): the before mixed pair
#   was re-run and agrees. The finishMax/blendedMax pairs on mixed data are under 1.3x; no
#   direction is read from them, they are here for their allocation.
#
