# Checks behind the vector rows:
# - Allocation: gc.alloc.rate.norm is ~0 B/op (under 0.02) for finish256, finish512, blended256
#   and blended512 on common data, so the vector body ran unboxed. finish256/512 on mixed data
#   allocate 52928 / 44032 B/op: that is the per-lane finish's toArray/fromArray, by design.
# - 128-bit rows are NOT vector code: they allocate 1.36-1.90 MB/op. -XX:+PrintIntrinsics shows
#   VectorSupport::compare/blend/test failing to intrinsify for 128-bit double masks on this JDK
#   (x86, also with -XX:UseAVX=2); a mask-free 128-bit loop (mul, add, div, D2L/L2D, shifts)
#   did intrinsify. Do not read the 128-bit rows as the port's speed.
# - Before the run, PrintIntrinsics showed calls into Lanes refused with NodeCountInliningCutoff
#   late in the body; the body now makes those calls first and writes the exponent add out,
#   after which the 256/512-bit rows above allocate nothing.
#
