# Log1pBenchmark on the owner's laptop under -XX:UseAVX=2, 2 November 2026: log1p's three arms
#
# LAPTOP NUMBERS, NOT HEADLINES. -XX:UseAVX=2 makes C2 compile as for an AVX2 host (GitHub's x86
# runners and the EPYC 7763 benchmark hosts): it clears the AVX-512 features, AVX512DQ included.
# The laptop's own datapath is 256 bits either way. Headline numbers come from the EPYC 7763.
# The same benchmark with the laptop's default flags (AVX-512) is in log1p-laptop-2026-11-02.txt.
#
# Commit:      the commit that adds this file (based on 3bd5e84); Log1p.java, VFdlibm.java,
#              Lanes.java and Log1pBenchmark.java are byte for byte as they were at the runs
# JDK:         OpenJDK 64-Bit Server VM (build 25.0.4.1+1-1-26.04.4-Ubuntu, mixed mode, sharing)
# CPU:         AMD Ryzen AI 9 HX PRO 370 w/ Radeon 890M (24 logical cores)
# Vector:      -XX:UseAVX=2 -XX:MaxVectorSize=32 (preferred species 256 bits)
# Kernel:      7.0.0-42-generic
# Load:        at the start and end of each run, below; each run waited for the one-minute load
#              to fall under 1.0 before starting. Other agents share the machine; their JVM work
#              goes through the same lock as these runs.
# JMH 1.37:    -f 2 -wi 3 -w 2s -i 5 -r 2s -prof gc
#              -jvmArgsAppend "-XX:CompileCommand=inline,io.github.vecbricks.vfdlibm.*::*
#              -XX:UseAVX=2 -XX:MaxVectorSize=32"
#              (the body inlined into the loop, as Varka emits it)
# Command:     java --add-modules jdk.incubator.vector -cp <test classpath> org.openjdk.jmh.Main
#              "Log1pBenchmark.(guarded256|finish256|blended256|scalarStrictMath) <the options
#              above>" (what mvn -B -Pjmh exec:exec runs)
# Array:       1024 doubles; common = uniform [-0.9, 20]; mixed = one input in 16 replaced by NaN,
#              -1, -2, 2^-40 or 1.0 (whose 1+x is a power of two, so |f| < 2^-20)
# Arms:        guarded = rare paths computed and blended only when a vector holds a rare lane
#              (VFdlibm.log1p); blended = rare paths computed and blended in every vector;
#              finish = rare lanes finished by StrictMath.log1p through toArray/fromArray
# Not run:     512 bits (no 512-bit vectors under UseAVX=2, so software); 128 bits (no mask
#              operation lowers at two 64-bit lanes on x86, SKILLS.md, so every arm boxes)
#
# Prediction, written after two short exploratory runs (the first is at the end of this
# header) and before the committed runs:
# nothing allocates on common data and only finish allocates on mixed (~52,928 B/op); guarded
# ties finish on common (~2.8 us), beats it on mixed by about 2x, and is within 1.3x of blended
# on both mixes (faster on common). It held.
#
# Checks:
# - bench/alloc-check.py --include 'Log1pBenchmark\.\w+(256|Preferred)$' --jvm-args
#   "-XX:UseAVX=2 -XX:MaxVectorSize=32 -XX:+UnlockDiagnosticVMOptions -XX:+PrintIntrinsics":
#   guarded, blended and finish at 256 bits and preferred (256 here) read 0.019 to 0.023 B/op at
#   most on common data. The same check with default flags passes too (0.011 to 0.018 B/op).
# - On mixed data guarded and blended stay at ~0.01 B/op; finish allocates 52,928 B/op, its
#   toArray/fromArray round trip, as exp's finish does.
# - PrintIntrinsics, scoped to the library with -Xbatch
#   (-XX:CompileCommand=PrintIntrinsics,io.github.vecbricks.vfdlibm.*::*), guarded256 on mixed
#   data under these flags: every VectorSupport call of the body (binaryOp, fromBitsCoerced,
#   blend, convert for L2I, I2L and I2D, compare, broadcastInt, test, load, store) printed
#   "(intrinsic) late inline succeeded", and no "not supported", "missing constant" or "unbox
#   failed" line was printed. The global -XX:+PrintIntrinsics of the allocation check also
#   prints "not supported: arity=1 op=store vlen=4 etype=double atype=byte" and the same for
#   etype=long; ExpBenchmark.finish256 under the same flags prints the same lines, so they come
#   from compiles outside the ports' bodies (no port stores into a byte array), and the rows
#   that printed them allocate ~0 B/op.
# - Re-run: every pair but finish on mixed data is within 1.3x, so the run was repeated with
#   the same options; the re-run's table follows the first. Ratios below are by minimums.
#
# Reading it, by minimums in ns per 1024 doubles at 256 bits, first run / re-run:
# - Common data: guarded 2760 / 2752, finish 2716 / 2732, blended 3185 / 3232, scalar
#   StrictMath.log1p 4723 / 4738. Guarded and finish are level (within 2%); blended is 1.15x and
#   1.17x behind; guarded is 1.7x faster than the scalar loop.
# - Mixed data: guarded 3011 / 3015, blended 3215 / 3198, finish 6038 / 5971, scalar 4560 /
#   4571. Guarded is 2.0x faster than finish, whose round trip allocates 52,928 B/op and makes it
#   1.3x slower than the scalar loop, and 1.06x to 1.07x faster than blended.
# - So the guarded arm is level with the fastest arm on common data and the fastest on mixed
#   data, and never allocates. VFdlibm.log1p uses it. The guarded-blended and guarded-finish
#   ratios are under 1.3x and held in both runs; the decision does not rest on them, since the
#   guarded arm is never behind either arm by more than 2% on either mix.
#
# Exploratory run, not part of the committed method (-f 1 -wi 3 -w 1s -i 3 -r 1s -prof gc,
# same flags, load not recorded), kept for the one number SKILLS.md quotes from it. It had a
# different finish arm: it read the rare lanes from rare.toLong() and wrote each
# StrictMath.log1p result back with result.withLane(lane, ...) in a loop over the set bits,
# beside the toArray/fromArray finish (finishArrays256). It allocated almost as much and was no
# faster, so it was replaced by the guarded arm. Its rows (ns/op), then gc.alloc.rate.norm:
