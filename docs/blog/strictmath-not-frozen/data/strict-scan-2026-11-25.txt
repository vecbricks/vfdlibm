# StrictMath and Math on JDK 21, 25, 26 and 27: which functions' bits moved

What was run and why: for the post "Even StrictMath is not frozen", which of StrictMath's double
functions (and Math's, with the JIT's defaults) return other bits on another JDK. It needs no
vfdlibm, so it covers JDK 21 too, and all of StrictMath's functions that may differ, not only
vfdlibm's 13. A bit comparison, not a timing. StrictMath's results do not depend on the CPU;
Math's do (the JIT's intrinsics are chosen per CPU), so the Math rows are this x86-64 laptop's
only, and an Arm host or another x86 CPU may give others.

Date: 25 November 2026
Host: laptop, AMD Ryzen AI 9 HX PRO 370 (flags: avx2 avx512f avx512dq), Linux 7.0.0-44-generic
JDKs: 21.0.13.1+2-1-26.04.1-Ubuntu, 25.0.5.1+2-1-26.04.1-Ubuntu, 26.0.2+10-2-26.04.2-Ubuntu
      (Ubuntu 26.04 packages) and 27.0.1.1+4-22 (jdk.java.net), each with its default flags
Inputs: StrictScan.java, the same inputs as JdkScan.java by the same seeds (its StrictMath.pow
      file on JDK 25 equals JdkScan's but on the both-NaN lanes, which StrictScan writes as 0),
      for 20 functions: sin cos tan asin acos atan exp log log10 sqrt cbrt sinh cosh tanh expm1
      log1p atan2 hypot pow IEEEremainder
Commands: javac -d . StrictScan.java (JDK 21); java -Xmx3g -cp . StrictScan <hard-cases> out-<jdk>
      on each JDK; python3 compare.py out-21 out-25 --all, and the same for 25 26, 25 27 and
      26 27

## Reading

- StrictMath returns the same bits on JDK 21, 25 and 26 for all 20 functions on every input here,
  and on JDK 27 for 19 of them. StrictMath.pow on JDK 27 differs on 1,258 inputs, the same ones
  as in jdk-scan-2026-11-25.txt, all in the set aimed at |y| > 2^31 with |x| near 1.
- Math, on this CPU, moved more often: cbrt and tanh from JDK 21 to 25 (on 198,346 and 523,661
  of 3,000,000 inputs), sinh from 25 to 26 (on 346,969 of 3,002,215), and none from 26 to 27.
  Math.pow, with its intrinsic, did not move.
