# Written by dev/coremath-hard-cases.py (its docstring says how to fetch the list), which checks the
# file's sha256, takes these of its lines, by the source's line numbers, in this order, and refuses
# any line that does not spell exactly one double per argument:
#   27102: the source's "worst-case for RNDN with 104 identical bits after the round bit": the exact
#     result within 2^-105 ulp of a midpoint; 1 pair written.
#   27109-27116: the source's "failures found by Eric Hennenhoefer using AI": exact ties, x*x + y*y
#     the square of a midpoint between two doubles; 8 pairs written.
#   27104: the source's "worst-case for RNDZ with 104 identical bits after the round bit": the exact
#     result within 2^-105 ulp of a double; 1 pair written.
#   23778, 25500, 25524, 25681, 25706, 26084, 26307, 26429, 26558, 26596: these ten lines, of the
#     source's section "worst cases with exp(y) = exp(x) - m with 1 <= m <= 27" (lines 385-26644,
#     26260 pairs): every pair of it whose exact result lies within 2^-60 ulp of a midpoint, as
#     measured when the list was evaluated (issue 144); 10 pairs written.
#
# No pair of these lines repeats another.
#
# Each pair is hard for correct rounding: hypot's exact result is a midpoint between two doubles, or
# lies within 2^-60 ulp of one, or within 2^-105 ulp of a double. HardCasePairsTest rechecks each of
# these claims with BigInteger arithmetic of its own, by the pair's place in this file.
#
# e_hypot.c does not round correctly (its error is below one ulp), so these pairs are no harder for
# a port that follows fdlibm's operations than any other pair; their use is that a dropped
# correction term or a reassociated sum, a change far below one ulp, is most likely to flip the
# result exactly at them. They are compared with StrictMath like every hard case, and nothing else
# is claimed of StrictMath's value.
